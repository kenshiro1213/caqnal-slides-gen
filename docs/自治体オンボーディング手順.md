# 自治体オンボーディング手順

新しい自治体（または新年度）のレポートを作るときの手順。全て `uv run caqnal <cmd> --client <自治体名>` で実行する。

> **v2（自治体共通版 2026-10-08）への移行中。** 現行仕様は `docs/仕様書/`（佐賀市サンプル準拠）。以下のコマンドは v1 実装のもの。v2 の工程（validate → normalize → aggregate → models → publish → compose → render → verify）は `docs/PLAN.md` の P1〜P7 で順に置き換える。
> 今の時点でも、v2 の原則に従って進めること:
> - **新案件として登録する。** 他の自治体や前年度の設定・例外対応・対象外・最低人数（佐賀市の 5 名など）・施策文をコピーしない。確認待ちの項目は `null` のまま残す（埋めただけで確定扱いにしない）
> - **受領時に記録する:** ファイルごとの担当・取得日・シート・ヘッダー行・SHA256。調査対象（雇用区分・対象外・休職等・母数の基準）。組織階層（兼務・直轄・異動の時点）。読者と閲覧範囲。基本方針の名称・改定日・頁
> - **未確定一覧:** 不明な対象者や設問対応はここに残す。数字の意味が変わる項目は処理を保留する
> - **最終 PPT の確認:** 数値と表示の全頁を確認し、確認記録と一緒に納品する

## 0. 受領ファイルを配置してリネーム
1. `local-governments/<自治体名>/data/` を作り、受領ファイルを `<年度>_<種別>[_<版・日付>][_PII].<ext>` にリネームして置く
2. `local-governments/<自治体名>/RENAME_MEMO.md` に 元名 → 新名 の表を追記
3. 個人情報を含むファイルは `_PII` サフィックス（gitignore で除外、パイプラインは読まない）

## 1. プロファイル（生データを開かずに済む要約を作る）
```
uv run caqnal profile --client <自治体名>
```
`data/` 内の CSV/xlsx ごとに `profile/<ファイル名>.md` を出力（encoding・行列数・全列名・欠損・値分布 top20。自由記述は件数と文字数のみ、値は出さない）。git 管理する。

## 2. 設問マスタと経年対応表の下書き
```
uv run caqnal init --client <自治体名> --questions data/R8_設問.xlsx [--sheet R8年度設問] --responses data/R8_回答.csv [--previous-questions data/R8_設問.xlsx --previous-sheet R7年度設問 --previous-responses data/R7_回答.csv]
```
- `questions.yaml`（当年度）と `questions_R7.yaml`（前年度、指定時）と `yoy_map.yaml` を生成
- xlsx 形式は自動判定（八戸市型 / 佐賀市型 / 十和田・板橋型）。判定できないときは `--adapter` で指定
- 生成後、人が確定する項目: `role`（outcome/driver/attribute/freetext）、`reverse`、`condition`、`yoy_map` の `status`（要確認 → 比較可/参考比較/比較不可）

## 3. client.yaml を書く
`local-governments/八戸市/client.yaml` をコピーして編集。最低限:
- `client.name / fiscal_year / fiscal_year_label / report_date / target_count`
- `data.responses / encoding / respondent_id / previous`
- `scales`（ラベル→スコア。**尺度の向き**を必ず確認。八戸市は①=5、佐賀市は5=5）
- `attributes`（属性設問と表示順）、`organization`（組織設問・単位名の表示順・階層）
- `indicators.overall_engagement.questions`、`segmentation`、`positioning`、`key_driver`、`comments`
- 仕様書 Appendix A の項目と1対1。閾値は `config/analysis_defaults.yaml` を継承し、案件固有の値だけ `analysis:` で上書き

## 3-2. v2 の案件設定を足す
`config/client_template.yaml` の各セクションを client.yaml に追記する。内容は inputs / population / publication / common9 / objectives / corrections / attribute_rules / org_dictionary / readers / models / unresolved。組織辞書 `org.yaml` も作る。
`uv run caqnal validate --client <自治体名>` の先頭に `[case] status=...` が出る。
- `blocked`: 構造の誤り（参照切れ・循環・重複 ID・SHA256 不一致など）。直すまで進めない
- `draft_unconfirmed`: 「未確定」の一覧を担当者に確認する
- `validated`: 入口の確認が済んだ

## 4. 検証 → 解析 → 描画
```
uv run caqnal validate --client <自治体名>     # 列対応・尺度・組織紐付け・匿名性・経年対応を検査
uv run caqnal analyze  --client <自治体名>     # output/intermediate/
uv run caqnal render   --client <自治体名> --pdf   # output/*.pptx, 部局別/, 分析手法解説_社内向け.pptx, *.xlsx, *.pdf
uv run caqnal all      --client <自治体名> --pdf   # validate→analyze→render
uv run caqnal verify-v1 --client <自治体名>    # 2回実行してハッシュ一致を確認（旧仕様。v2 は caqnal verify）
uv run caqnal render   --client <自治体名> --font meiryo --pdf   # フォント切替版（output/font_meiryo/）
```

## 5. 納品前
- `output/intermediate/settings_snapshot.yaml` と `summary.json` を納品物に含める（仕様書13 処理ログ・設定値）
- `git status` で `data/` `output/` `_PII` が追跡されていないことを確認してコミット（client.yaml / questions*.yaml / yoy_map.yaml / profile/ / RENAME_MEMO.md は追跡する）

## デッキ構成を変えるとき
`config/decks/全庁.yaml` 等のスライドリストを編集する（`手法解説.yaml` は社内向けの分析手法解説）。自治体固有の構成にしたい場合は `client.yaml` の `deck_overrides: {全庁: decks/全庁.yaml}` のように自治体側のパスを指定すると優先される（例: 佐賀市は属性・所属・自由記述設問が無いため、該当章を除いた `local-governments/佐賀市/decks/全庁.yaml` を使う）。
